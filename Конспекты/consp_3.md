## 6.1. Основные понятия и принципы тестирования ПО

**Тестирование** — процесс выполнения программы с целью обнаружения ошибок. Шаги процесса задаются **тестами**.

**Каждый тест определяет:**
- свой набор исходных данных и условий для запуска программы;
- набор ожидаемых результатов работы программы.

Другое название теста — **тестовый вариант**.

**Исчерпывающее тестирование** — полная проверка программы: все наборы исходных данных, все варианты их обработки. Требует огромного количества тестовых вариантов. На практике часто невозможно из-за **ресурсных ограничений** (прежде всего, по времени).

**Хороший тестовый вариант** — тест с высокой вероятностью обнаружения ещё не раскрытой ошибки.
**Успешный тест** — тест, который обнаруживает до сих пор не раскрытую ошибку.

**Цель проектирования тестовых вариантов** — систематическое обнаружение различных классов ошибок при минимальных затратах времени и стоимости.

### Что может и чего не может тестирование

**Тестирование обеспечивает:**
- обнаружение ошибок;
- демонстрацию соответствия функций программы её назначению;
- демонстрацию реализации требований к характеристикам программы;
- отображение надёжности как индикатора качества программы.

**Тестирование не может показать отсутствия дефектов** — оно может показывать только присутствие дефектов. Важно помнить это (скорее печальное) утверждение при проведении тестирования.

## 6.2. Информационные потоки процесса тестирования

На входе процесса тестирования — **три потока**:
- текст программы;
- исходные данные для запуска программы;
- ожидаемые результаты.

**Схема процесса (рис. 6.1):**

```
Текст программы ─┐
                 ├─► Тестирование ─► Оценивание ─► Отладка ─► Исправления
Исходные данные ─┘         ▲              │
                           │              ▼
                  Ожидаемые результаты   Модель надёжности
                                    (Интенсивность ошибок)
```

Выполняются тесты, все полученные результаты оцениваются: **реальные результаты сравниваются с ожидаемыми**. При несовпадении фиксируется ошибка — начинается **отладка**.

**Особенности отладки:**
- Процесс отладки непредсказуем по времени: на поиск места дефекта и исправление может потребоваться час, день, месяц.
- Неопределённость в отладке приводит к большим трудностям в планировании действий.

**Оценка качества и надёжности ПО после сбора результатов:**
- Если регулярно встречаются серьёзные ошибки, требующие проектных изменений → качество и надёжность ПО подозрительны, необходимо усиление тестирования.
- Если функции реализованы правильно, а обнаруженные ошибки легко исправляются, возможны два вывода:
  1. качество и надёжность ПО удовлетворительны;
  2. тесты не способны обнаруживать серьёзные ошибки.

Если тесты не обнаруживают ошибок, появляется сомнение в том, что тестовые варианты достаточно продуманы и что в ПО нет скрытых ошибок. Такие ошибки будут в конечном итоге обнаруживаться пользователями и корректироваться разработчиком на этапе сопровождения — когда **стоимость исправления возрастает в 60–100 раз** по сравнению с этапом разработки.

**Модели надёжности ПО** — формальный способ оценки результатов тестирования: выполняют прогноз надёжности по реальным данным об интенсивности ошибок.

## 6.3. Два принципа тестирования

1. **Функциональное тестирование** (тестирование «чёрного ящика»).
2. **Структурное тестирование** (тестирование «белого ящика»).

---

## 6.4. Тестирование «черного ящика»

**Известны:** функции программы.
**Исследуется:** работа каждой функции на всей области определения.

Основное место приложения тестов «чёрного ящика» — **интерфейс ПО** (рис. 6.2): входы `X` → `F(x)` → выходы `Y`.

**Тесты демонстрируют:**
- как выполняются функции программ;
- как принимаются исходные данные;
- как вырабатываются результаты;
- как сохраняется целостность внешней информации.

При тестировании «чёрного ящика» рассматриваются **системные характеристики** программ, **игнорируется внутренняя логическая структура**.

**Проблема исчерпывающего тестирования:** если в программе 10 входных величин и каждая принимает по 10 значений, потребуется **10¹⁰ тестовых вариантов**.

Тестирование «чёрного ящика» **не реагирует на многие особенности программных ошибок**.

---

## 6.5. Тестирование «белого ящика»

**Известна:** внутренняя структура программы.
**Исследуются:** внутренние элементы программы и связи между ними (рис. 6.3).

**Объект тестирования** — не внешнее, а **внутреннее поведение** программы. Проверяется корректность построения всех элементов программы и правильность их взаимодействия друг с другом. Обычно анализируются **управляющие связи** элементов, реже — информационные.

Тестирование «белого ящика» характеризуется **степенью, в какой тесты выполняют или покрывают логику (исходный текст) программы**. Исчерпывающее тестирование также затруднительно.

---

## 6.6. Особенности тестирования «белого ящика»

Обычно основано на **анализе управляющей структуры программы**. Программа считается полностью проверенной, если проведено исчерпывающее тестирование маршрутов (путей) её графа управления.

**Формируются тестовые варианты, в которых:**
- гарантируется проверка всех независимых маршрутов программы;
- проходятся ветви True, False для всех логических решений;
- выполняются все циклы (в пределах их границ и диапазонов);
- анализируется правильность внутренних структур данных.

### Недостатки тестирования «белого ящика»

1. **Количество независимых маршрутов может быть очень велико.** Если цикл выполняется `k` раз, а внутри цикла имеется `n` ветвлений, количество маршрутов:

   $$m = \sum_{i=1}^{n} n_i$$

   При `n = 5` и `k = 20` количество маршрутов `m = 10¹⁴`. При затрате 1 мс на тест по одному маршруту при работе 24/7/365 на тестирование уйдёт **3170 лет**.

2. Исчерпывающее тестирование маршрутов **не гарантирует соответствия программы исходным требованиям** к ней.

3. В программе могут быть **пропущены некоторые маршруты**.

4. **Нельзя обнаружить ошибки, зависящие от обрабатываемых данных** (например, `if abs(a-b) < eps...`, `if (a+b+c)/3 = a...`).

### Достоинства тестирования «белого ящика»

Принцип «белого ящика» позволяет **учесть особенности программных ошибок**:

1. Количество ошибок **минимально в «центре»** и **максимально на «периферии»** программы.
2. Предварительные предположения о вероятности потока управления или данных часто некорректны — типовым может стать маршрут, модель вычислений по которому проработана слабо.
3. При записи алгоритма на языке программирования возможны **типовые ошибки трансляции** (синтаксические и семантические).
4. Некоторые результаты в программе зависят **не от исходных данных, а от внутренних состояний** программы.

Каждая из этих причин — аргумент для проведения тестирования по принципу «белого ящика». Тесты «чёрного ящика» не смогут реагировать на ошибки таких типов.

## 6.7. Способ тестирования базового пути

**Тестирование базового пути** — способ, основанный на принципе «белого ящика». Автор — **Том МакКейб (1976)**.

**Даёт возможность:**
- получить оценку **комплексной сложности** программы;
- использовать эту оценку для определения **необходимого количества тестовых вариантов**.

Тестовые варианты разрабатываются для проверки **базового множества путей** (маршрутов) в программе. Они гарантируют **однократное выполнение каждого оператора** программы при тестировании.

---

## 6.8. Потоковый граф

Для представления программы используется **потоковый граф**.

**Особенности:**
1. Граф строится отображением управляющей структуры программы. Закрывающие скобки условных операторов и операторов циклов (`end if; end loop`) рассматриваются как отдельные (фиктивные) операторы.
2. **Узлы (вершины)** соответствуют линейным участкам программы, включают один или несколько операторов.
3. **Дуги** отображают поток управления (передачи управления между операторами). Дуга — ориентированное ребро.
4. Различают **операторные** и **предикатные** узлы. Из операторного узла выходит одна дуга, из предикатного — две.
5. **Предикатные узлы** соответствуют простым условиям. **Составное условие** (с OR, AND) отображается в несколько предикатных узлов.
6. **Регионы** — замкнутые области, образованные дугами и узлами.
7. Окружающая граф среда рассматривается как **дополнительный регион**.

**Пример преобразования составного условия** `if a OR b then x else y end if`:
- Прямое отображение (рис. 6.4) — один предикатный узел `a OR b`.
- Преобразованный потоковый граф (рис. 6.5) — два предикатных узла `a` и `b`, три региона **R1, R2, R3**.

### Пример 1. Процедура сжатия

```
процедура сжатие
1  выполнять пока нет EOF
2    читать запись;
3    если запись пуста
4    то удалить запись;
5    иначе если поле a >= поля b
6    то удалить b;
7    иначе удалить а;
7a   конец если;
7a   конец если;
7b   конец выполнять;
8  конец сжатие;
```

Потоковый граф (рис. 6.6) имеет **четыре региона**.

## 6.9. Цикломатическая сложность

**Цикломатическая сложность** — метрика ПО, обеспечивающая количественную оценку **логической сложности** программы. В способе тестирования базового пути определяет:
- количество **независимых путей** в базовом множестве программы;
- **верхнюю оценку количества тестов**, гарантирующего однократное выполнение всех операторов.

**Независимый путь** — любой путь, который вводит новый оператор обработки или новое условие. В терминах потокового графа независимый путь должен содержать **дугу, не входящую в ранее определённые пути**.

> **ПРИМЕЧАНИЕ.** Путь начинается в начальном узле и заканчивается в конечном узле графа. Независимые пути формируются в порядке от самого короткого к самому длинному.

### Независимые пути для графа из примера 1

| Путь | Маршрут |
|---|---|
| Путь 1 | 1-8 |
| Путь 2 | 1-2-3-7a-7b-1-8 |
| Путь 3 | 1-2-4-5-7a-7b-1-8 |
| Путь 4 | 1-2-4-6-7a-7b-1-8 |

Каждый новый путь включает новую дугу. Все независимые пути графа образуют **базовое множество**.

### Свойства базового множества

1. Тесты, обеспечивающие его проверку, гарантируют:
   - однократное выполнение каждого оператора;
   - выполнение каждого условия по True-ветви и по False-ветви.
2. Даёт **априорную оценку** количества независимых путей, которое имеет смысл искать в графе.

### Три способа вычисления цикломатической сложности

1. **По количеству регионов** потокового графа.
2. **По формуле:**
   $$V(G) = E - N + 2$$
   где `E` — количество дуг, `N` — количество узлов.
3. **По формуле:**
   $$V(G) = p + 1$$
   где `p` — количество предикатных узлов в графе `G`.

**Проверка для примера 1:**
1. 4 региона;
2. `V(G) = 11 дуг − 9 узлов + 2 = 4`;
3. `V(G) = 3 предикатных узла + 1 = 4`.

**Цикломатическая сложность графа = 4.**

## 6.10. Шаги способа тестирования базового пути

**Иллюстративная программа — процедура вычисления среднего значения:**

```
процедура сред;
1.  i := 1;
2.  введено := 0;
3.  колич := 0;
4.  сум := 0;
    вып пока [2 - вел(i) <> stop] и [введено <= 500 - 3]
5.    введено := введено + 1;
      если [5 - вел(i) >= мил] и [вел(i) <= макс - 6]
6.    то колич := колич + 1;
7.       сум := сум + вел(i);
8.    конец если;
9.    i := i + 1;
10. конец вып;
    если колич > 0
11. то сред := сум / колич;
12. иначе сред := stop;
13. конец если;
    конец сред;
```

Процедура содержит **составные условия** (в заголовке цикла и условном операторе). Элементы составных условий для наглядности помещены в рамки.

**Шаг 1.** На основе текста программы формируется потоковый граф:
- нумеруются операторы текста;
- производится отображение пронумерованного текста в узлы и вершины потокового графа (рис. 6.7).

### Ключевые числа

- Стоимость исправления ошибки на этапе сопровождения **в 60–100 раз** выше, чем на этапе разработки.
